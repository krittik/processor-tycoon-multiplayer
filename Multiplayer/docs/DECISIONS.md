# Decisions

Binding decisions for the Multiplayer mod. To change one, add a new entry that supersedes it (`Supersedes D#`) and update ARCHITECTURE.md in the same change. Status: **accepted**, **proposed** (needs a spike or data), **superseded**.

Context: decided with the user on 2026-09-27 after comparing lockstep, dumb-client, host-simulated snapshot and ownership-split designs.

| ID | Decision | Why | Status |
|---|---|---|---|
| D1 | Standalone plugin `ProcessorTycoon.Mp` in `Dev/Multiplayer/`, independent of the Agent mod (code, versioning, docs, rules). | Different purpose and rules (the MP mod needs internal state access); ship separately. | accepted |
| D2 | Star topology. Host = world owner + clock + arbiter; peers connect only to the host. Every machine runs the full simulation. Target 2–8 players. | N connections instead of N²; one place for ordering and conflicts; native UI works because every machine has live objects. | accepted |
| D3 | Ownership split: each player is authoritative for their own company; the host for the world. Player actions are not intercepted, except actions on host-owned shared objects, which become host commands. | Intercepting ~40 UI-embedded actions (no command layer in the game) was the main cost of every other design. | accepted |
| D4 | Remote human companies are ghost `AICompany` instances with AI and simulation muted. | Market and all UI already treat AI companies as rivals; market code has no `IsPlayer` branches. | accepted |
| D5 | Replication uses the game's own `JsonUtility`: per-entity JSON, top-level key diff, apply with `FromJsonOverwrite`. Scope derived from `SaveObject` ("if it's in the save, it's in MP"). | No per-type serializers; object identity preserved (no scene reload, UI stays open); game updates that add saved state are covered automatically. | accepted |
| D6 | Time control is host-only in the first versions: peers' speed buttons are non-interactable and mirror the host. Admin-configurable time control later. | Simplest correct option. | accepted |
| D7 | Native dialog pause is disabled during a session. | Otherwise any player's CPU designer stalls everyone or pushes them out of the lag window. | accepted |
| D8 | A lagging peer catches up by fast-forwarding up to `R` days (default 30); beyond that, or after reconnect, snapshot resync. | Fast-forward is cheap for small gaps; snapshot is robust for large ones. | accepted |
| D9 | Only the host creates a new world (including history fast-forward); peers join by snapshot. | One source of truth; no RNG agreement needed. | accepted |
| D10 | Host owns save truth. Monthly checkpoints are written on every machine after hash agreement, so any player can resume alone or become host. MP saves live in `Saves/Multiplayer/<session>/*.ptmp`, invisible to the vanilla loader. | User requirement: continue without the original host; vanilla must never load a ghost-company save (it would fail on the unknown company template). | accepted |
| D11 | Game-wide settings (difficulty, cheats) follow the host. Cheats off by default. Per-player automation preferences stay per player (they only affect the owner's company). | Fairness and consistency. | accepted |
| D12 | Trusted peers. No anti-cheat or plausibility checks in the first slice. | Friends-only play; keep the prototype fast. Open/competitive games may come later. | accepted |
| D13 | Transport behind `ITransport`: Loopback (tests), TCP (development, LAN, direct IP), Steam lobby + relay on AppID 480 (release). App id via `SteamAppId` env var. | Local testing needs no Steam; Spacewar dependency stays replaceable. | accepted |
| D14 | Public interop API (`ProcessorTycoonMp.Api`); the Agent mod integrates as a soft dependency; the Agent CLI drives scripted multi-client tests. | Mod cooperation and automated testing. | accepted |
| D15 | Automatic hash check on the first day of each month; mismatch triggers automatic resync and desync report. No user-triggered checks. | User preference; turns bugs into hitches while producing evidence. | accepted |
| D16 | Cross-platform by design: only the Steam native library is platform-specific and sits behind the transport. | BepInEx Mono runs on Windows, Linux, macOS. | accepted |
| D17 | The game developer (CoffeeHeaven) explicitly allows this kind of mod (requested on their Discord). Never ship game files or decompiled code. | Distribution permission. | accepted |
| D18 | Use BepInEx's shared HarmonyX (no fork, no bundling). Patches are applied only during a session and removed after. Prefix/postfix; `return false` only for clock/muting; transpilers only with a new decision. | Coexistence with other mods; single player untouched. | accepted |
| D19 | Muting = filtering `DateController` event invocation lists by delegate target (swap in prefix, restore in postfix) + per-item prefixes for shared iterators (e.g. project ticks). Unclassified handler targets are reported. | Generic, no skip of central methods, and exposes new systems added by game updates. | accepted (S3 + live runs) |
| D20 | Slot-partitioned SaveIDs: `slot × 10,000,000 + n`; host keeps the native counter. | Prevents ID collisions between machines creating entities concurrently. | accepted |
| D21 | Strict version lock at handshake: game version, `Assembly-CSharp` hash, MP mod version, protocol version, simulation-affecting mods. Client-side mods (Agent mod) allow-listed. | Only identical code can stay in sync; no cross-version compatibility burden. | accepted |
| D22 | Core has no third-party dependencies: own minimal JSON scanner, `BinaryWriter` codec, `DeflateStream`. | Avoid assembly version clashes with other plugins (e.g. the Agent mod ships Newtonsoft.Json). | accepted |
| D23 | The plugin compiles against a publicized `Assembly-CSharp` (BepInEx.AssemblyPublicizer.MSBuild); only `Adapter/` uses it. | Direct, compile-checked access to private members instead of string reflection; breaks at build time after game updates. | accepted |
| D24 | Market results: owner-authoritative first; switch to host-authoritative if measured drift is visible with 4+ players. | Simplest first; contained fallback. | accepted — measured 2026-09-27: 105% sales difference on peers while AI production was muted, 5.5% after D47 (1995, 2 players) |
| D25 | Disconnected player's company is taken over by the AI until they return. Host loss pauses the session; resume from cached checkpoint with a new host (automatic migration later). | Keeps games alive without complex migration in the first slice. | accepted |
| D26 | Plugin GUID `processortycoon.multiplayer`, name "Processor Tycoon Multiplayer". Fixed before first public release. | Other mods and configs depend on the GUID. | accepted |
| D27 | Lag window `K`: 0 (strict daily barrier) in the first playable slice, default 2 afterwards. Checkpoint days always use `K=0`. | Correctness first, then latency tolerance for 4+ players. | accepted |
| D28 | M0 experiments live in a separate plugin `spikes/ProcessorTycoon.Mp.Spikes` (GUID `processortycoon.multiplayer.spikes`), triggered by Ctrl+Shift hotkeys, reporting to the BepInEx log. Built with the solution, deployed only into testbeds, never packaged. | Experiments need code running inside the game; keeping them out of the real plugin stops throwaway code from leaking into the mod. | accepted |
| D29 | Live tests run only in disposable testbeds (`artifacts/testbeds/<name>`) created by `scripts/new-testbed.ps1` from the official game zip (source of truth), with BepInEx copied from the main install and the Agent mod on its own port (A = 17617 host, B = 17618 peer; main game keeps 17616). Fixture saves live in `fixtures/saves/` (repo-level, `mpfx-*`). | Reproducible clean game, main game folder never touched, testbeds addressable by the Agent CLI in parallel. | accepted |
| D30 | Snapshots travel as one `Snapshot` message (deflated save JSON, e.g. 4 MiB → 330 KiB in 1995), not Begin/Chunk/End. Supersedes the chunking in PROTOCOL. | TCP frames up to 64 MiB; simpler. Revisit for Steam message limits in M4. | accepted |
| D31 | MP saves are the game's own save JSON (`.txt`), written and loaded through `SaveHandler`: `Saves/Multiplayer/<session>/checkpoint-s<slot>-<date>.txt` (last 3 per slot; each machine writes its own view) plus `session.txt` (roster with client ids). Supersedes the `.ptmp` container of D10. | Native load path, no converter to maintain; the folder is still invisible to the vanilla loader. | accepted |
| D32 | Checkpoints repair before they hash: every machine keeps a mirror of each remote entity (the owner's last known JSON), overwrites local drift with it and logs the drifted fields; only differences that survive the repair (apply bugs, ownership disagreements) cause a resync and a desync report. Snapshots are built after a repair too. Extends D15. | Local simulation writes into remote entities (market sales, world systems) and owners do not resend unchanged keys. | accepted |
| D33 | Contracts (available pool, active contracts) are player-local in the first slice: each machine keeps its own pool; they are neither replicated nor hashed, and a peer's active contracts survive its resync loads. Supersedes the "contract pool" row of ARCHITECTURE's ownership table until M3. | Contract generation uses unseeded RNG and player UI; a shared pool needs host commands (M3). | superseded by D43 |
| D34 | Daily capture budget: full capture on checkpoint eves; otherwise AI companies round-robin every 3 days and AI CPUs every 5 days (since D47), retired CPUs reuse their last capture, and month-scale history lists (`FinancialReports`, `Factory.MonthlyReports`) keep the value of the last full capture. | Late saves: host capture 760 → ~130 ms/day, peer apply ~8 MB → <1 MB/day; rival data a few days old is invisible. | accepted |
| D35 | After any snapshot load the host sets `DayBundle.ResendAll`: every owner (host and peers) resets its delta tracker and sends full upserts once. | Loading normalizes state (report lists, trimmed CPU data); diffs against pre-load baselines would never repair it. | accepted |
| D36 | A joining player's company is created by the host as a clone of the host's company state (new name, colour, slot-range SaveID, UniqueID `MPGHOST-<slot>`). Sessions are meant to start from a new game (fair start); a mid-game joiner inherits the host's current company state (known limitation). | No game code creates a fresh player company mid-game; cloning uses the save converters. | accepted (revisit) |
| D37 | On peers, handlers of the host-only world systems `CompanySpawner` and `CompanyEventHandler` are muted (they create or destroy companies); all other world systems run everywhere (deterministic per the RNG inventory). Companies simulated elsewhere are muted on every machine. | Minimal host-only set; their effects on remote companies are overwritten by the owners. | accepted |
| D38 | The version check (D21) compares protocol, MP mod version, `MpProtocol.TargetGameVersion` + `Application.version` (the game reports "0.2.0"), the first 16 hex chars of the `Assembly-CSharp` SHA-256, and the sorted GUID@version list of plugins that are not allow-listed. | `Application.version` alone cannot tell game builds apart. | accepted |
| D39 | The first UI is an IMGUI window (F9 or the button in the top bar) for host / join / resume / leave / chat / status; scripted tests use `<game>/mp-dev/cmd.txt` and `status.json` (active only when `mp-dev/` exists). | Enough to play and test now; a native-looking UI comes later (M4/M5). | accepted |
| D40 | Architecture ownership (`Architecture.OwnerIDs`, keyed by UniqueID) is canonicalized: `PLAYER` ↔ `MPGHOST-<local slot>` on capture, apply and in snapshots. | Every machine's own player is "PLAYER" locally. | accepted |
| D41 | Checkpoint hashes stay monthly (D15), but when writing a checkpoint save took more than 400 ms (late eras: ~0.9 s for a 14 MB world), each machine writes only every third month; the session record is written every month. | A monthly one-second stall at 3–4 days/s is too frequent; resume granularity of a quarter is acceptable. | accepted |
| D42 | Exception to D18: the two load hooks (ghost spawn for `MPGHOST-*` ids, player SaveID from the save) are installed for the whole game run. They only act on multiplayer data. | A save made after leaving a session (or a copied checkpoint) contains ghost companies and must stay loadable; ghosts then load as ordinary AI rivals. | accepted |
| D43 | Supersedes D33. One shared contract pool owned by the host: tenders are replicated as `Contract` entities (key = FNV of template index + client name), `ContractManager` (generation, acceptance, termination) runs only on the host (D37), and peers' offers/withdrawals (native UI or contract automation) are sent as `Command` messages and applied by the host, which re-validates them. Winners get the native "contract signed" popup on their own machine. | Contracts are tenders where AI and players compete; per-player pools let non-host players win every tender unopposed. | accepted |
| D44 | Architecture ownership granted to a peer's player by the game (x86-64 cross-licensing agreement, `ArchitectureManager`) is sent to the host as an `architecture-owner` command; the host adds the player's ghost id to `OwnerIDs`, which replicates through the market entity (D40). | Market data is host-owned; a peer's local grant would be overwritten. | accepted |
| D45 | Business contracts are host-owned `BusinessContract` entities (key = FNV of type, provider, client, start date); `BusinessContractManager` is host-only on peers. A deal the local player signs or breaks on a peer becomes a `business-add` / `business-break` command. Cross-company production: the production handlers of a provider company also run on the machine of each human client with an active foundry deal (Muting), so the client's own CPUs are produced there; everything else that run touches is remote and overwritten by its owner. Deals between two human players are refused (the game would accept them with AI logic on behalf of the other human). | Makes AI foundry services and other AI deals work for every player; no consent flow between humans exists yet. | accepted |
| D46 | Supersedes the refusal part of D45: a deal between two players needs the other player's consent. The negotiation window shows that the other player decides instead of an AI score; signing sends the deal as a proposal on the internal channel `mp.deal`. The other player gets an Accept/Decline prompt (dev command `deal accept|decline`). Acceptance becomes the `business-add-approved` command (or a direct add on the host), and a decline is reported on `mp.deal-declined`. | Player-to-player foundry deals without either side being overruled by AI logic. | accepted |
| D47 | Factory handlers (the `InitializeFactory` closures: client/contract/market production, operating cost, daily production reset, monthly report) run for every company on every machine; all other company handlers stay muted on non-owners (D19). Subsumes D45's provider rule for these handlers. | Muted AI production left AI CPUs out of stock between owner updates, so peers' local markets under-sold rivals (D24 drift 105% → 5.5%). Production is deterministic; its effects on remote entities are overwritten by the owners. | accepted |
| D48 | A full resend (`ResendAll`) upserts every owned entity and still emits Removes for entities removed since the last bundle (tracker `Produce(full: true)` instead of `Reset`). | A reset forgot sent entities, so a contract removed on the resend day stayed on the peers forever (found by the 4-player soak). | accepted |
| D49 | Checkpoint hashes use each machine's own entities as last sent (delta tracker state) and remote entities as held locally. | Player actions between the last sent delta and the checkpoint (e.g. releasing a CPU between frames) made the owner hash state nobody else had yet (found by the 4-player soak; regression test). | accepted |
| D50 | Steam transport (M4): Steamworks.NET 2025.164.1 standalone (MIT, Windows x64, with Valve's redistributable `steam_api64.dll`) is fetched by `tools/fetch-steamworks.ps1` into `artifacts/lib/` with a pinned SHA-256, never committed, and shipped next to the plugin. Steam starts lazily when the panel opens or a Steam address is used (AppID 480 via environment variables, native library loaded by full path first). The host opens a friends-only lobby only for discovery (friends list, "Join game"); players connect with `SteamNetworkingSockets` P2P to the host's Steam id through the relay. Frames travel as fragments of at most 256 KiB with a one-byte "more follows" header (Core `Fragments`). Addresses: `steam` (host), `steam:<id>` (join); `steamip:` runs the same transport over Steam IP sockets for one-account tests on one PC. A disposed host keeps its listen socket 5 s so lingering connections close gracefully. | No port forwarding; friends find each other without addresses. Keeps TCP working when Steam is absent; resolves D30's "revisit for Steam message limits". | accepted |
| D51 | A company belongs to a slot only through the session roster (`PlayerInfo.CompanyId`); the `MPGHOST-<slot>` unique id decides only before a roster exists. A new slot-N player continues a slot-N company left in the world by an earlier session; otherwise new player companies get a free id in the slot's range. | A save made after a session keeps the other players' companies as `MPGHOST-<slot>` AI rivals; hosting from it treated them as players (frozen companies) and gave the next joiner a colliding company id (found while testing Steam). | accepted |
| D52 | In-progress projects of human companies (CPU, factory expansion, custom hardware, continuous; they live in `TimerScheduler`, not in company entities) travel as a **carried** entity kind `Projects` (7): the machine simulating the company sends it whole whenever it changes; receivers only store it (no drift repair, no checkpoint hash). Every save written during a session (snapshot, checkpoint, manual) replaces the projects of human companies simulated elsewhere with the latest carried copy (prefix on `JsonUtility.ToJson` for `SaveObject`). When a player disconnects, the host restores their carried projects into its world so the AI continues them (D25), and the world is the source again. Technology research is company state (`ResearchSector`) and was already replicated. Protocol 5. | A peer's unfinished CPU was lost on rejoin, resync and resume (found by the Agent-mod test on the laptop): only released CPUs were entities. | accepted |
| D53 | Ghost companies keep only technologies they researched: after spawning (Ghosts.AfterSpawn) and after every load (LoadHooks, `SaveHandler.Load` → `OnLastLoadedTick`), technologies not in the ghost's replicated research are removed from its derived lists (wafers, nodes + node optimizations, packages, memories, frequencies, caches, multicores), the inverse of `AICompany.AddTechnology`. | `AICompany.Initialize` unlocks the historical template's technologies up to its late technology year and the lists are never rebuilt. `FactoryUpgradeHandler` then upgraded ghost lines toward 300 mm wafers every day: masked while the owner overwrote it (the ever-present `Company.Factory` drift repair), ~$50M/month of construction during an AI takeover (a laptop company went from -$19M to -$351M and bankrupt). | accepted |
| D54 | Host-local game code must not change the shared clock or shared objects: `DateController.ResumeAndOverride` (closing the Default warning, "Select New Research") is skipped during a session; a new player's company gets its own `Divisions` object. | Found in the 8-player run: the host's company went into default and closing the warning paused everyone for minutes; `SaveObjectInstantiator.InstantiateToSave` hands out the company's live `Divisions` and `UnpackFromSave` adopts it, so every player company created on the host shared the host company's divisions (one player selling their factory made the host "fabless"; the resulting mismatch resynced all 7 peers). | accepted |
| D55 | A disconnected player's company is kept by a **caretaker** on the host for `Session.CaretakerDays` (default 182, half a year): the company is simulated (production, sales, research progress, costs, running projects) but no AI decision runs for it (handlers of `ProcessorTycoon.AISystem` components muted; `TriggerPriceUpdate`, `SellProductionLinesToAvoidBankruptcy`, `CancelAllProjects`, `BankruptcyWarning`, `ConsiderGoingFabless` refused). After that the AI plays it until the player returns (D25). The roster carries `OfflineSince` and `AiControl`; every player sees the countdown and gets native notifications for joins, disconnects, returns, the AI taking over and bankruptcies. Protocol 6. | User decision after the 8-player run: during a few minutes away the AI repriced a player's CPU to $339 and switched production off. | accepted |
| D56 | After a resync snapshot a peer writes back the members of its own entities (company, CPUs, custom hardware) that differ from its pre-load capture, after taking the snapshot as its baseline, so the next delta sends them to the host. The first load and a rejoin keep the host's copy (the host simulated the company meanwhile). | The host's copy of a peer's entities trails by up to the lag window; a resync reverted a player's production lines set just before it. | accepted |
| D57 | A bankrupt human company is frozen like a bankrupt AI company: its projects are unscheduled, released CPUs retired, research stopped; `TimerScheduler.Schedule` refuses new projects of bankrupt companies. The native Game Over (only "Return To Menu", which would end the session, for everyone on the host) is replaced by a notice: the player stays and watches, or leaves. | User decision; in the 8-player run a bankrupt player's construction kept running (-$83M to -$865M) and the host's own bankruptcy offered only a session-ending button. | accepted |
| D58 | A new player founds their company on the game's own New Game screen (`MenuGameSetup`), opened in the main menu with the host's difficulty, date and cheats locked; its Start button (relabelled Join, `GameManager.StartNewGame` prefix) sends a `CompanySetup` (name, founder, colour, company type, funds, factory size and starting technology from the screen's difficulty table) and the host creates the company only then: a new-game company founded now (research unlocked like `Company.InitializeAsNewGame` from the current year, funds, factory lines on the newest wafer, empty history). The slot is held during setup and freed if the player leaves. Scripted joins compute the same values from the screen (`JoinSetup.Auto`). Supersedes the host-company clone of D36. | Players could not choose CPU, fabless or foundry, and a mid-game joiner inherited the host's whole company. | accepted |
| D59 | The mod's UI is uGUI on its own overlay canvas drawn with the game's resources: Roboto fonts, the RoundCorners42 sprite with the native corner scales (windows 3, buttons 5, scrollbars 4, inputs 10), the shadow sprite, native icons, the current `ThemeManager` palette (light and dark), the hand cursor, native tooltips (`TooltipTrigger` with runtime `TooltipData`) and native notification popups (`PopupManager.InstantiateGenericNotification`). Entry points: a tray entry in the bottom bar (left of the Agent mod's), a Multiplayer item in the main menu (copy of the Settings button with its own click event) and F9. Player-led companies get a person icon with a tooltip after their name wherever the game shows it; the name text itself is untouched (the Agent mod reads it). Nothing is built in headless games. Replaces the IMGUI panel. | User request: the same style as the Agent mod and the game's windows. | accepted |
| D60 | When ownership of entities moves to another machine (a player returns and takes their company back from the host), the delta tracker forgets them instead of reporting them removed; entities that really disappeared are still reported. | The host sent `Remove` deltas for a returning player's company and CPUs; receivers ignored them (removals of companies and CPUs are never applied), so harmless, but wrong. | accepted |
| D61 | The mod's windows follow layout rules shared with the Agent mod (since D63 in the Mod API's docs/CONVENTIONS.md): title bar × is the only Close; a main window's footer holds the version link (About) and window-wide actions; a status line (dot, short text) comes first; explanations sit in info-icon tooltips; a choice between modes or presets is a strip in the game's tab style; at most one blue button per section; body 15, secondary 14, fine print 13, controls 28 px. Tooltips of the mod's own windows are drawn on the mod's canvas in the native tooltip's look, so they always show above the mod's windows; the game's own texts (player tags) keep native tooltips. Diagnostics moved to About next to Report an issue. | User request: proper hierarchy, less text, useful information, tooltips with icons, both mods alike. | accepted |
| D62 | Chat is an on-screen feed at the bottom left during a session (fading lines above an input line that stays on screen, hidden while the Pause Menu is open, hovering the input line shows the history, mouse wheel scrolls back, Enter or a click on the input line writes; opt out with `Chat.Overlay` or the window's checkbox, which moves chat back into the Multiplayer window with notifications). `@Name text` is a private message: `Chat` carries a recipient (protocol 7) and the host relays it only to that player, who gets it as an email conversation (`Mail`, key per player, Reply opens the chat). Business proposals between players arrive as emails with the Email window's own Accept/Decline buttons and a notification instead of a modal prompt; unanswered after 30 game days they are declined automatically (`mp.deal-expired` tells the proposer). The mod's emails live in memory only and are kept out of every save. Supersedes the proposal prompt of D45 and the chat notices of D55. | User request: an always-visible chat like the agent feed that does not clutter, private messages through Email, less invasive deal offers that can be answered later. | accepted |
| D63 | The mod's UI is built with the Processor Tycoon Mod API, a separate open-source repository whose source every mod compiles in (vendored with git subtree in `ModApi/`; all types internal, so copies in several mods never clash). It replaces this mod's Look/Kit/Window/Tray code and the Agent mod's AgentUi; cross-mod cooperation (bottom-bar order, email IDs) goes through plain runtime names listed in its CONVENTIONS.md. | One implementation and look for both mods and for other modders, without a runtime dependency players would have to install. | accepted |
